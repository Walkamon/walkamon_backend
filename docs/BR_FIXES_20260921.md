# BR fixes - 2026-09-21

## Changes

- Reject existing JWTs for non-active or soft-deleted accounts on subsequent authenticated requests.
- Serialize friend mutations with ordered SQL user-row locks; only pending requests can be accepted, rejected or cancelled. Friendship and request status save together.
- Serialize purchases with wallet/inventory update locks; use the existing purchase primary key for retry deduplication.
- Respect push opt-out for immediate and scheduled broadcasts, without deleting the user's in-app notification history.
- Exclude disabled/deleted accounts from pet rankings; recheck account activity when accepting Sprint invites.
- Exclude inactive evolution targets without skipping over an inactive first/next stage; preserve stage-zero starter lookups.
- Save business changes and audit records in one atomic SaveChanges; include every part of composite keys. Clear rolled-back tracked state before retrying a transaction.
- Require today's eligible steps to meet the effective walking goal before streak claim. Recompute streak inside the transaction; claim once per Vietnam calendar date.

## Purchase API compatibility

`POST /api/shop/buy` accepts an optional non-empty UUID `requestId` alongside `shopItemId` and `quantity`.

Clients must generate the ID **before** the first submission and reuse it with the same payload for all retries of that purchase. A new intentional purchase must use a new ID. A reused ID with a different owner/item/quantity is rejected. The response adds `purchaseId`; on replay, price/quantity are from the original purchase while wallet/inventory values reflect current stored state. Replay does not charge or grant again, even if the shop entry has since been disabled.

Legacy clients without `requestId` remain compatible but cannot be deduplicated across independent HTTP retries. Server-side transaction retries retain the same generated purchase ID. No schema migration or production SQL is required. Mobile was not changed in this backend-only task.

## Runnable regression checks

Uses existing .NET/SQL Server dependencies; no added test framework or NuGet package. The console runner restores the previously missing solution project with executable assertions.

```powershell
sqllocaldb start WalkamonValidation
dotnet run --project Walkamon.IntegrationTests/Walkamon.IntegrationTests.csproj
dotnet build Walkamon.sln --configuration Release
```

If the LocalDB instance does not exist, create it once with `sqllocaldb create WalkamonValidation`. The runner creates/deletes only its own randomly named `WalkamonBRChecks_*` database, starts a localhost API with isolated settings and no background workers, and uses a fake push sender. It never reads the application's database connection configuration or sends real notifications.

Checks cover concurrent purchase retries/distinct requests/overspending, payload mismatch, retry after rollback, audit failure with and without an outer transaction, bidirectional friend requests, terminal request rejection, concurrent accepts, removal/replay, goal eligibility and concurrent claims, rankings, inactive stages, immediate/scheduled push opt-out, and a real JWT reused before/after disabling its account.

Verified locally on 2026-09-21: 28 checks passed; full solution Release build succeeded with 0 errors and the 8 existing warnings (nullable annotations and obsolete Google/FCM APIs). No live database or real push service was used.

Live production deployment, real FCM delivery, existing SignalR connections, client adoption of `requestId`, and Mobile UI behavior are not validated by this local runner. Existing unrelated Level-cap and other audit findings are not included in these fixes.
